Executive Summary

The BlockFinaX smart contract system is well-structured and reflects a mature understanding of the Diamond (EIP-2535) pattern, MasterChef-style accounting, and DeFi security primitives. Most critical patterns — CEI ordering, nonReentrant, SafeERC20, and fee snapshots — are applied correctly throughout. The issues identified below are real, but the majority are medium or low severity. There is no single catastrophic flaw. However, several issues compound to create meaningful risk and should be addressed before scaling liquidity significantly.

Critical Findings

C-01
DiamondCutFacet is never replaced by TimelockCutFacet — selector collision
BlockFinaXDiamondCutFacet and BlockFinaXTimelockCutFacet both expose diamondCut(FacetCut[],address,bytes). The comment states the timelock "replaces" the old facet via a DiamondCut action, but that replacement must itself be performed using the original instant diamondCut. If the original facet is never removed, both share the selector and the Diamond's routing is undefined. If the original is removed first but the timelock has not yet been installed, upgrades are temporarily impossible.

Recommended fix: Document this as an explicit deployment invariant and enforce it with a constructor or initializer check that verifies both facets cannot be registered simultaneously. The deployment script must sequence the transition atomically.
C-02
facetAddress() in LoupeFacet returns a potentially corrupted address
In BlockFinaXDiamondLoupeFacet.facetAddress(), the line facetAddress_ = ds.selectorToFacetAndPosition[_functionSelector] assigns from a mapping to an address variable. This compiles correctly only if selectorToFacetAndPosition is declared as mapping(bytes4 => address) in LibDiamond. Many EIP-2535 reference implementations store mapping(bytes4 => FacetAddressAndPosition) (a struct), which would make this a silent type error — the loupe would return a corrupted or zero address for all function-selector lookups.

Recommended fix: Verify the actual LibDiamond storage declaration. If the mapping stores a struct, extract .facetAddress from it explicitly: facetAddress_ = ds.selectorToFacetAndPosition[_functionSelector].facetAddress.

High Severity

H-01
withdrawCapital does not prevent subsequent premium claims
An LP can call withdrawCapital before calling claimPremiums. The withdrawal sets dep.withdrawn = true and decrements totalActiveShares, but dep.shares is never zeroed. Any subsequent call to claimPremiums on the same depositId will succeed — there is no dep.withdrawn check in claimPremiums — and compute accrued premiums based on the non-zero share count, effectively paying the LP twice for their capital.

Recommended fix: Either zero dep.shares on withdrawal, or add require(!dep.withdrawn, "Capital withdrawn") at the top of claimPremiums.
H-02
recoverExpiredPayouts uses stale totalLiquidity after LP withdrawals
withdrawCapital does not decrement evt.totalLiquidity. After multiple LPs withdraw, totalLiquidity still reflects the original deposited sum while the actual USDC balance held by the contract is materially lower. When recoverExpiredPayouts sweeps any residual amount into hedgePlatformFeesCollected, it can create a phantom balance — a fee balance that withdrawPlatformFees will attempt to transfer but cannot, causing a revert.

Recommended fix: Reconcile platform fee accounting against the actual token balance of the contract rather than against in-storage counters. Alternatively, decrement evt.totalLiquidity on each withdrawCapital call.
H-03
Oracle RESUBMIT_COOLDOWN does not reset after consensus is cleared
lastSubmitTime[_eventId][msg.sender] is set on every submitRate call but is never cleared by _clearSubmissions. After a disagreement clears the submission round, each oracle must still wait the full RESUBMIT_COOLDOWN (5 minutes) from their last submission before retrying. In a scenario where oracles rapidly disagree and the round clears repeatedly, legitimate re-settlement can be delayed 5 minutes per round with no recourse for the owner other than calling clearStaleSubmissions — which itself does not reset lastSubmitTime.

Recommended fix: Clear lastSubmitTime entries within _clearSubmissions, or provide an owner-callable emergency function that resets cooldowns for specific oracles and events.

Medium Severity

M-01
Misleading comment — Diamond owner cannot settle after activateOracleV2()
The comment in setOracleAdmin states "The Diamond owner always retains the ability to settle regardless of this setting." This is incorrect. After activateOracleV2() sets oracleV2Active = true, the require(!s.oracleV2Active) check in settleEvent rejects all callers — including the Diamond owner — because the check runs after the onlyOracleAdmin modifier. Operators who rely on the comment as documentation may believe they have a fallback they do not have.

Recommended fix: Remove or correct the misleading comment to accurately reflect that activateOracleV2() is a one-way lock for all settlement paths.
M-02
buyProtection uses user-supplied initialRate for payout calculation
The initialRate parameter in createEvent is provided by the event creator without any on-chain oracle validation. A creator could set an artificially low initialRate to make priceDelta = strike - initialRate very large, thereby making each hedger's predeterminedPayout disproportionately large relative to the premium paid. This is a misconfigured-event risk rather than a direct exploit, but it could drain LP capital on a legitimate-looking event.

Recommended fix: Consider requiring an on-chain oracle price confirmation at event creation, or enforcing a maximum priceDelta as a bounded percentage of initialRate (e.g. no more than ±50%).
M-03
deposit() share calculation truncates to zero for small deposits
The formula shares = (_amount * evt.totalActiveShares) / evt.totalLiquidity can truncate to zero when totalLiquidity is large relative to _amount. For example, with a 1,000,000 USDC pool and a 10 USDC deposit, the result may round to zero shares. A zero-share deposit permanently locks the LP's capital — withdrawCapital returns dep.amount net of lpPayoutShare, but claimPremiums yields zero indefinitely.

Recommended fix: Add require(shares > 0, "Deposit too small relative to pool size") immediately after the share calculation.
M-04
TimelockCutFacet proposal IDs can collide in the same block
The proposalId is derived from keccak256(abi.encode(_facetCuts, _init, _callData, block.timestamp, block.number)). Two proposals submitted in the same block with identical cut data produce the same proposalId, causing the second call to revert with "Proposal already exists." An adversary can front-run a legitimate upgrade proposal with an identical one, effectively blocking the upgrade for the duration of the current block.

Recommended fix: Add an incrementing nonce counter to TimelockStorage and include it in the hash input. This makes every proposal ID unique regardless of timing or data.
M-05
LP withdrawal fairness asymmetry between early and late withdrawers
claimPayout reduces evt.totalMaxPayout using grossPayout, which was already accounted for at buyProtection time. This is intentional and documented. However, if LPs call withdrawCapital after only some hedgers have claimed, those LPs are penalised for unclaimed payouts that were already deducted from the pool during capital withdrawal. Early LP withdrawers bear the cost of pending payouts; late withdrawers benefit after those payouts reduce totalMaxPayout.

Recommended fix: This is a design-level trade-off rather than a strict bug. Consider documenting the withdrawal ordering behaviour explicitly in user-facing material, and evaluate whether a snapshot-based payout reserve approach would be fairer.

Low Severity

L-01
getPendingCutIds() array grows unboundedly
Every diamondCut proposal appends to ts.ids. Cancelled and executed proposals are never removed. Over time this array could become expensive to iterate off-chain and could eventually hit gas limits if on-chain enumeration is ever added.

Recommended fix: Remove executed and cancelled proposal IDs from the array, or maintain a separate index mapping to mark their status and skip them during iteration.
L-02
LoupeFacet.facets() has O(n·m) read complexity
facets() iterates all facets, and within each facet facetFunctionSelectors iterates again — producing O(n·m) complexity. For the current deployment size (5–15 facets, 10–50 selectors each) this is acceptable. However, significant Diamond expansion could make this call costly.

Recommended fix: Low priority at current scale. Monitor as the facet count grows and consider a pagination approach if read cost becomes problematic.
L-03
rescueETH does not cap forwarded gas
_to.call{value: balance}("") forwards all remaining gas. If _to is a contract with a malicious fallback, this could be exploited in a gas-griefing scenario.

Recommended fix: Use a gas-capped call: _to.call{value: balance, gas: 2300}(""). This is the standard safe pattern for ETH rescue functions.
L-04
PayoutClaimed event does not index eventId
PayoutClaimed indexes positionId and hedger but not eventId. Off-chain indexers must join through getHedgePosition to link a claim to its parent event, adding an extra RPC call per claim.

Recommended fix: Add eventId as an indexed field. Up to three indexed parameters are available per event with no ABI encoding overhead.
L-05
setPoolSettings lacks nonReentrant
The function does not transfer tokens and is guarded by whenNotPaused, but it is inconsistent with the rest of the state-changing surface which applies nonReentrant throughout.

Recommended fix: Add nonReentrant for defence-in-depth against any future logic changes that may introduce token transfers.

Informational / Gas

I-01
Unused storage slot — totalHedgeEvents
totalHedgeEvents is retained in storage for layout compatibility per a comment but is never read. It can be removed in a future storage migration to reclaim one storage slot (~20,000 gas saving on first write operations that would otherwise touch that slot).
I-02
Duplicated deposit logic in _createInitialDeposit and deposit()
Both functions share nearly identical logic but are separate code paths. A bug fix applied to one may be missed in the other. Refactoring both into a shared internal _createDeposit helper would eliminate this maintenance risk.
I-03
recoverExpiredPayouts may consume significant gas
The function loops over all positions up to MAX_POSITIONS_PER_EVENT = 500. It is owner-only and non-time-critical, so this is acceptable in practice. Callers should be aware of gas usage when calling on events with many positions and may need to split the call.
I-04
_checkConsensus makes two passes over submitters
The function makes two full iterations over submitters — one to count valid entries and one to collect them. A single pass with a dynamic memory-push approach would halve iterations. Given the 10-oracle cap, the gas impact is negligible at current scale but may matter if the oracle set is ever expanded.

Strengths

  • The fee snapshot mechanism correctly prevents retroactive fee changes from affecting in-flight events.
  • The MasterChef-style accPremiumPerShare accumulator is a significant gas improvement over O(n) loops and is implemented correctly.
  • CEI (Checks-Effects-Interactions) ordering is applied consistently across all state-changing functions.
  • The nonReentrant modifier uses the Diamond-compatible shared AppStorage lock rather than a contract-level variable — the correct approach for delegatecall architecture.
  • The 90-day grace period with recoverExpiredPayouts is a thoughtful solution to the locked-funds problem.
  • Two-step ownership transfer prevents accidental lockouts of the Diamond owner role.
  • The oracleV2Active one-way flag provides a clean migration path to full oracle decentralisation.
